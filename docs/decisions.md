# Журнал решений

Контекст для тех, кто (или что) будет менять проект дальше: почему сделано именно так и что осталось незакрытым. Дополняйте при каждом значимом изменении.

## Авторизация: от общего токена к JWT

**Было.** Скрипт админки отправлял `Authorization: Bearer btoa(имя_папки_админки)`, сервер сравнивал строку с `SERVER_BEARER_TOKEN`. Секретом фактически было имя папки — оно видно в URL, в реферерах и в логах прокси. Если переменная не задана, `undefined === undefined` пропускал любой запрос без заголовка.

**Стало.** Модуль PrestaShop подписывает короткоживущий JWT (HS256) на текущего сотрудника и отдаёт его странице через `Media::addJsDef`. Сервер проверяет подпись, `exp`, `iss`, `aud`.

**Почему HS256, а не RS256.** Приватный ключ в любом случае лежал бы в БД PrestaShop, поэтому асимметрия не добавляет защиты, а добавляет операционной возни.

**Ограничение.** Аутентификация есть, авторизации нет. Любой сотрудник с доступом к странице заказа может создать отправку и счёт. Градация по профилям обсуждалась (список профилей в настройках / штатный ACL через скрытый Tab / claim `scope` в токене) и отложена: на практике админкой пользуются администраторы.

## Перевозчики: id_reference вместо названий

Определение перевозчика сравнением `textContent` с русской строкой ломалось при смене темы, языка админки или переименовании тарифа.

`id_carrier` тоже не подходит: PrestaShop при правке перевозчика помечает старую запись `deleted = 1` и создаёт новую с новым id. Стабилен только `id_reference` — он копируется в новую запись (`Carrier::copyCarrierData`).

Полезный побочный эффект: у старых заказов `id_carrier` указывает на удалённую запись, но `new Carrier()` её загружает, и `id_reference` разрешается корректно — кнопки работают и на архивных заказах.

## Регистрация отправок 5Post

Отправка регистрируется рекомендуемым API `POST /api/v3/orders`, а не устаревшим `createOrder`. На один заказ PrestaShop создаётся одно грузоместо; пункт выдачи берётся из последнего сообщения с сохранённым виджетом идентификатором `[ID: ...]`.

`partnerLocationId` склада отправителя настраивается в модуле PrestaShop, а не в окружении NestJS. Модуль передаёт его серверу в подписанном JWT сотрудника: настройка не приходит отдельным полем из браузера и не может быть подменена. После изменения настройки сотрудник должен обновить страницу заказа, чтобы получить новый JWT. При отсутствии настройки отправка не создаётся и сотрудник получает понятную ошибку.

Заказ передаётся как предоплаченный (`paymentValue: 0`, `paymentType: PREPAYMENT`). Штрихкод грузоместа из ответа 5Post показывается сотруднику как трек-номер; 5Post генерирует его сам, если это разрешено для партнёра.

## Сборка модуля

Клиентские скрипты собираются прямо в `views/js/` модуля. Раньше их копировали в тему и в модуль Custom Code вручную.

Оба файла собираются одним проектом. Какое-то время была раздельная компиляция через два tsconfig — из-за `module: none` файлы делят глобальную область и одноимённые функции конфликтовали. От этого отказались: конфиги с нестандартными именами не подхватываются языковым сервисом TypeScript, и редактор показывал несуществующие ошибки при зелёной сборке. Вместо этого админские аналоги функций получили суффикс `Admin`.

`target` зафиксирован на `es2020`. При более низком значении TypeScript разворачивает `?.` на верхнем уровне в глобальный `var _a`. Бандл виджета Яндекс.Доставки объявляет собственный `const _a`, что даёт `SyntaxError: Identifier '_a' has already been declared` — бандл не выполняется целиком, `window.YaDelivery` не появляется, и карта открывается пустой. Диагностика заняла время именно потому, что симптом (схлопнувшаяся вёрстка) находится далеко от причины (конфликт имён в глобальной области), а админка при этом работала: в `backend.ts` не было конструкций верхнего уровня, требующих хелпера.

Упаковка вынесена в `scripts/pack-module.ps1`:

- `powershell -Command` внутри npm-скрипта терял кавычки при передаче через cmd и молча ничего не делал, возвращая код 0. Заменено на `-File`.
- `Compress-Archive` и `ZipFile::CreateFromDirectory` на .NET Framework пишут `\` в именах записей. PHP не видит структуру папок, PrestaShop отвечает «Этот файл не является архивом модуля». Имена формируются вручную с `/`.
- Скрипт ASCII-only: PowerShell 5.1 читает `.ps1` без BOM как ANSI и падает на кириллице.

## Витрина

Виджеты ПВЗ переехали из модуля Custom Code в наш модуль (хук `actionFrontControllerSetMedia`). Скрипт витрины к shop-server не обращается — только рисует карты и пишет адрес в комментарий к заказу, поэтому вопрос авторизации там не стоит.

Клик по ссылке «Карта пунктов ...» выбирает перевозчика и **ждёт** события темы `updatedDeliveryForm`, прежде чем открыть карту. Раньше ссылка лежала внутри `<label>`: выбор радиокнопки запускал аякс-перерисовку формы, и ответ мог затереть textarea с только что записанным адресом пункта. Баг воспроизводился через раз, в зависимости от того, как быстро покупатель выбирал пункт.

Контейнер карты Яндекса получил `height: auto` (модификатор `--auto`): виджет сам задаёт высоту через `size.height`, и при фиксированной высоте контейнера вылезал за его границы, перекрывая кнопку закрытия. У 5Post поведение обратное — он растягивается по контейнеру, поэтому базовый класс сохранил фиксированную высоту.

## Ошибки и диагностика

Раньше сервис отдавал наружу сырой объект ошибки (`data: error`) со стектрейсами и внутренними адресами, а админка показывала `alert('Не удалось создать счёт')`. Сотрудник видел факт ошибки, но не мог передать разработчику ничего пригодного.

Сейчас каждому запросу присваивается короткий `requestId`, который уходит в лог и в заголовок `X-Request-Id`. Сотрудник видит понятный текст и может скопировать блок с деталями; разработчик по этому id находит в логах полный контекст со стектрейсом.

Решения, которые легко нечаянно откатить:

- `requestId` всегда генерируется сервером. Принимать его из входящего заголовка нельзя — это подделка связки и инъекция в логи.
- В CORS добавлен `exposedHeaders`: без него браузер не отдаёт заголовок скрипту и id пропадает.
- В копируемый блок деталей нельзя класть JWT: сотрудник вставляет его в чат.
- Для 5xx наружу уходит только «Внутренняя ошибка сервера»; текст исходной ошибки остаётся в логе.

Витрина сознательно не трогалась: покупателю технические детали бесполезны. Автоматическая отправка ошибок в Telegram обсуждалась и отложена до понимания, какие ошибки реально случаются; приёмник ошибок обязан быть закрыт гардом и троттлингом, иначе это канал спама в рабочий чат.

`AppService.failure()` изначально не логировал `requestId` — сервисы не имеют доступа к объекту запроса, а делать их `REQUEST`-scoped ради одного поля означало бы пересоздавать все сервисы на каждый HTTP-запрос. Решено через `AsyncLocalStorage` (`src/common/request-id.storage.ts`): `RequestIdMiddleware` оборачивает `next()` в `requestIdStorage.run(id, next)`, и `getCurrentRequestId()` работает из любого сервиса внутри цепочки того же запроса без изменения сигнатур. В тело ответа requestId не дублируется — клиент и так получает его из заголовка `X-Request-Id`, который выставляется на **любой** ответ, включая `200` с `ok: false`.

## Среда

PrestaShop работает на PHP 8.1.32 (обновлено с 7.4.33 в 2026-09, понижение не планируется).

Сервер живёт на Render. Таймаут в клиенте (15 с) и формулировка «операция могла всё же выполниться» — следствие холодных стартов.

## Таймауты на внешних вызовах

Все вызовы идут через `fetchWithTimeout` (`src/common/fetch-with-timeout.ts`, 10 с по умолчанию). Раньше таймаутов не было ни в одном сервисе: зависший API любого перевозчика исчерпывал пул воркеров, и магазин терял сразу и счета, и отправки.

Точка врезки в каждом сервисе одна — метод `fetchData`; исключения — `FiveService` (три места из-за логики обновления токена) и `DpdService` (SOAP). В DPD таймаут задаётся дважды: на загрузку WSDL через `wsdl_options` и на сам вызов — зависнуть может любой из них.

Хелпер различает таймаут и сетевую ошибку (`ExternalRequestTimeoutError`) — сотруднику нужны разные формулировки: после таймаута операция могла всё же выполниться на стороне перевозчика.

Заодно в `BotService.fetchData` появилась проверка `response.ok` — это был единственный сервис без неё, и при 429 от Telegram тело ошибки шло дальше как успешный ответ.

## Ошибка в раннем аудите: «открытые» контроллеры

В первоначальном аудите `ShopController` и `YaController` были отмечены как критическая утечка ПДн: файлы содержат `@Get('customer/:id')` и подобное без гардов. **Это было неверно.** Оба контроллера закомментированы в `@Module({ controllers })`, то есть их роутов в рантайме никогда не существовало.

Урок: наличие файла с `@Controller` и декораторами маршрутов ничего не говорит о доступности эндпоинта. Единственный источник правды — регистрация в модуле.

## CRON пересмотра статусов

Внешний сервис расписания не получает `SHOPSERVER_JWT_SECRET` и не подписывает JWT сам. Он вызывает `POST /module/shopserver/cron` на магазине с уникальным ключом в заголовке `X-ShopServer-Cron-Key`. Модуль сравнивает ключ через `hash_equals`, сам выпускает JWT на 5 минут с `sub: prestashop-cron` и `scope: orders:revise`, после чего вызывает серверный `POST /revise`. Прокси модуля ждёт ответ сервера до 300 секунд: полный пересмотр статусов занимает дольше обычного внешнего API-вызова.

JWT с этим scope допускается только к пересмотру: `CronReviseJwtGuard` блокирует обычные JWT сотрудников на `/revise`, а `EmployeeJwtGuard` блокирует технический токен на действиях сотрудника. Это предотвращает превращение ключа CRON в универсальный ключ API.

Ключ генерируется при установке и обновлении модуля 1.3.0, показывается только в настройках модуля и может быть перевыпущен. После перевыпуска его нужно обновить в сервисе расписания.

В версии модуля 1.5.0 добавлен ручной запуск пересмотра из вкладки «Проверка статусов». Он создаёт такой же технический JWT, как CRON, и вызывает `POST /revise` с тем же лимитом ожидания 300 секунд. Так можно проверить путь без передачи ключа CRON в браузер и сверить результат с журналом Render.

Вкладки настройки передают стандартный `AdminModules` token в URL. Без него PrestaShop отклоняет переход GET с сообщением «Неверный токен безопасности» до запуска кода модуля.

Ручной пересмотр показывает безопасно экранированный результат `/revise` в админке. HTTP 200 означает, что запрос выполнился, но не обязательно что был изменён статус; результат нужен, чтобы отличить отсутствие изменений от ошибки сопоставления или статуса.

В версии 1.5.3 кнопка ручного пересмотра не запускает валидацию формы настроек. Несопоставленная отправка Яндекс.Доставки теперь возвращается в отчёте `/revise`, а не остаётся только в журнале Render.

При пересмотре перевозчик Яндекс.Доставка определяется также по `operator_request_id` из ответа API, сопоставленному с `reference` заказа. Формат `shipping_number` в PrestaShop не всегда UUID Яндекса, поэтому использовать его как единственный признак нельзя.

Яндекс начал добавлять `#` перед UUID в `shipping_number`. Классификатор принимает оба формата: UUID и `#UUID`.

## Пункт приёма Яндекс.Доставки

`platform_id` пунктов приёма Ростова и Тулы настраиваются в модуле PrestaShop, а не в коде сервера. Модуль включает оба значения в подписанный JWT сотрудника (`yaSourcePlatformIds`). Сервер получает актуальный статус заказа через PrestaShop API и выбирает `rnd` для статуса `12`, `tul` для статуса `13`. Таким образом, настройка не передаётся из браузера и не требует перезапуска сервера.

После изменения настройки сотрудник должен обновить страницу заказа, чтобы получить новый JWT. Для модуля, обновлённого до 1.4.1, оба поля нужно заполнить перед созданием новой отправки. Обновление переносит прежнее единое значение в оба поля только как временную заготовку; его необходимо заменить корректными ID Ростова и Тулы.

## Терминалы отправки DPD (2026-09)

До версии модуля 1.11.0 терминалы отправки DPD (Ростов/Тула) были захардкожены в enum `DpdSourceTerminal` на сервере (`2N83`/`095H`) — единственные значения такого рода, которые не читались из модуля, в отличие от `yaSourcePlatformIds`/`fivePostSenderLocation`. Приведено к тому же паттерну, что и Яндекс.Доставка: `SHOPSERVER_DPD_SOURCE_TERMINAL_RND`/`_TUL` — новые поля на вкладке «Доставка», обязательны только при выбранном перевозчике DPD (как проверка ID склада 5Post). Значения включаются в подписанный JWT сотрудника (`dpdSourceTerminalIds`) и в ответ `botorders` для Telegram-бота — сервер по-прежнему не хранит ID перевозчиков в коде или переменных окружения.

`AppService.createDpdOrder` выбирает `rnd`/`tul` по `current_state` заказа (12/13) той же функцией, что и `createYaOrder` — при отсутствии настройки для статуса возвращает `HttpException` с понятным сообщением вместо падения с ошибкой SOAP. `convertOrderToDpd` больше не знает о статусах заказа: терминал отправки передаётся уже разрешённой строкой, как `sourcePlatformId` у `convertOrder`.

Поскольку добавлены новые ключи `Configuration`, версия модуля поднята до 1.11.0 с `upgrade/upgrade-1.11.0.php` (в отличие от правки кнопки DPD в 1.10.0, где новых ключей не было).

## Email-уведомления о статусе

В версии модуля 1.6.0 отправка клиентских email-шаблонов перенесена из отдельного модуля в `shopserver`. Он слушает `actionObjectOrderHistoryAddAfter` и сравнивает новый статус с двумя настраиваемыми парами «статус — шаблон»: для ожидания получения и доставки.

Выбрана точка `OrderHistory`, а не вызов из NestJS: сервер меняет статус через PrestaShop Webservice, который создаёт историю заказа и вызывает этот хук. Поэтому одно правило действует для пересмотра статусов по API, CRON и ручной смены статуса в админке. Это намеренно: письмо описывает изменение статуса, а не его источник.

В каждом поле шаблона указывается имя файла из `/mails/<язык>/` без языкового суффикса. В шаблон передаются `{firstname}`, `{lastname}`, `{order_name}` и `{id_order}`. `Mail::Send` может вернуть `false` без исключения, поэтому обе формы ошибки записываются в журнал PrestaShop.

## Автоматическая запись трек-номера

До версии модуля 1.9.0 сотрудник после создания отправки в Яндекс.Доставке или 5Post копировал трек из буфера обмена и вручную вставлял его в поле трекинга на странице заказа — только так PrestaShop отправлял письмо клиенту со ссылкой на отслеживание. Запись того же поля через webservice (`PUT /api/order_carriers/:id`) вызывает `update()` объекта, но родное письмо всё равно не уходит: логика его отправки зашита в `AdminOrdersController`, а не в модель `OrderCarrier`, и webservice её не проходит.

Решение то же, что и для статусов: перехват объектного хука `actionObjectOrderCarrierUpdateAfter`. Он срабатывает и на правку в БО, и на PUT через webservice, поэтому одно правило письма работает независимо от источника изменения. `AppService.createYaOrder`/`createFivePostOrder` теперь сами вызывают `ShopService.updateOrderCarrierTracking` сразу после получения трека от перевозчика — employee JWT для этого не нужен, пишет тот же Basic-токен webservice, которым сервис уже читает заказ.

Функция read-modify-write: PrestaShop на PUT ожидает полный XML ресурса, а не только изменённое поле, поэтому перед записью используется уже загруженный `getOrderCarrierInfo` (id, id_carrier, id_order_invoice, вес, стоимость доставки) — как и на странице заказа, где это же значение сначала читается для формы.

Письмо шлётся с шаблоном из отдельного поля `SHOPSERVER_NOTIFY_TRACKING_TEMPLATE` (вкладка «Уведомления»), а не переиспользует шаблоны статусов waiting/delivered — у него другой набор переменных: `{tracking_number}` и `{follow_url}` (URL перевозчика с подставленным треком через `Carrier::$url`). Поле пустое по умолчанию — уведомление выключено, пока шаблон не создан и не указан явно.

Ошибка записи трека не должна ронять создание отправки: `writeTrackingNumber` в `AppService` ловит исключение, шлёт предупреждение сотруднику в Telegram с треком для ручной вставки и возвращает `ok: true` — сотрудник и так получает трек в буфер обмена как раньше.

Отправка письма не проверяет, что трек до этого был пустым: повторная запись (например, исправление опечатки) снова пришлёт письмо. Это осознанно — в отличие от статусов, трек в этом потоке пишется сервером один раз сразу после создания отправки, а не многократно фоновым пересмотром.

**Незакрытое требование окружения.** Ключ webservice, которым пользуется `SHOP_TOKEN`, должен иметь право на `PUT /order_carriers` в Административная панель → Расширенные параметры → Webservice — иначе запись трека будет молча падать в лог сервера (см. «Известные недоработки» — наружу уходит только «внутренняя ошибка сервера»), а письмо не уйдёт.

## Регистрация отправок DPD (createOrder2, 2026-09)

До этой версии `DpdService` умел только `getStatesByDPDOrder` — методы и DTO для создания заказа были начаты раньше, но никогда не доводились до рабочего состояния и не были проверены по реальной схеме. Перед реализацией схема `createOrder2` (`https://ws.dpd.ru/services/order2?xsd=1`) была скачана и сверена напрямую — в частности, внешний тег запроса оказался `orders` (не `request`, как у трекинга), а `cargoWeight`/`cargoVolume`/`cargoValue` в XSD объявлены как `xs:double`, а не строки, как было в старом DTO.

Используется `createOrder2`, а не `createOrder`: он дополнительно возвращает `pickupDate`/`dateFlag`, при этом входные параметры идентичны. Ответ `return` объявлен в XSD как `maxOccurs="unbounded"` даже когда в запросе один заказ; `node-soap` в этом случае иногда разворачивает массив из одного элемента в голый объект — `DpdService.createOrder` нормализует оба варианта и возвращает первый (единственный) результат.

По 54-ФЗ каждая позиция заказа обязана попасть в `unitLoad` с реальным наименованием товара (`descript`) — иначе DPD не сможет сформировать фискальный чек. Конвертер строит `unitLoad` из `order_rows` так же, как `convertFivePostOrder` строит `productValues`, и параллельно считает `cargoValue` как сумму цен позиций.

Пункт выдачи DPD (`terminalCode` в `receiverAddress`) получается тем же способом, что и для Яндекс.Доставки/5Post — через `findPointId` по сообщениям заказа. Это работает, потому что виджет `DPDChooser` на витрине (front.ts) и в админке (backend.ts, добавлено вместе с этой функциональностью) пишет `[ID: <departmentCode>]` в текст сообщения по тому же соглашению.

`serviceVariant` зафиксирован как `ТТ` (терминал-терминал): сотрудник сам отвозит отправление в терминал DPD, как и в существующей (неиспользуемой) черновой реализации — `senderAddress.terminalCode` берётся из `DpdSourceTerminal.RND`/`TUL` по тому же правилу, что и источник Яндекс.Доставки (`current_state` 12/13).

Категория груза настраивается через `DPD_CARGO_CATEGORY` (по умолчанию «Косметика») — старое значение «Минеральная пудра» было заменено, так как ассортимент шире одного товара.

Кнопка «Зарегистрировать отправку» и карта пунктов DPD добавлены в админку по аналогии с Яндекс.Доставкой/5Post (`order_actions.tpl`, `backend.ts`, `dpdSid` в конфиге `hookDisplayAdminOrderTop`). Регистрация в Telegram-боте (`/register`) реализована следом, в той же версии — см. следующий раздел.

## Наложенный платёж DPD (НПП, 2026-09)

Из подключённых перевозчиков наложенный платёж (оплата при получении) поддерживает только DPD — Яндекс.Доставка и 5Post создаются с жёстко заданным «уже оплачено» (`already_paid`/`PREPAYMENT`), поэтому вопрос раньше не возникал. Для DPD это нельзя было игнорировать: часть заказов уходит в доставку с способом оплаты «Выставить счёт» до того, как счёт фактически оплачен.

Признак неполной оплаты — разница `total_paid − total_paid_real` из `ShopOrderInfo` (та же пара полей, которую для этой же цели уже использовал закомментированный черновик `sum_npp` в старом, нерабочем коде создания DPD-заказа). Если разница больше 1 копейки (защита от плавающей точки), `convertOrderToDpd` добавляет в заказ `extraService: [{ esCode: 'НПП', param: [{ name: 'sum_npp', value: <остаток> }] }]` — DPD соберёт эту сумму с получателя и переведёт её магазину. Если заказ оплачен полностью, `extraService` не добавляется вовсе (как было раньше).

`НПП` требует объявленной стоимости (`cargoValue`), которая в конвертере уже считается из `unitLoad` — дополнительных изменений для этого не потребовалось.

`AppService.createDpdOrder` после успешной регистрации явно читает `sum_npp` обратно из построенного `order[0].extraService` (не пересчитывает сумму заново) и добавляет предупреждение в `data.message`, которое сотрудник увидит в админке/боте — это должно исключить ситуацию, когда сотрудник вручную требует оплату при получении, хотя её уже соберёт курьер (или наоборот, забывает, что деньги ещё не поступили).

## Проверка статусов DPD (isReturn, 2026-09)

До этой правки `AppService.getDataForRevise` намеренно исключал DPD из автосинхронизации статуса (`order.cargo !== Cargos.DPD` в `reviseOrders`): `newState` (`OnTerminal`, `OnTerminalDelivery`, `OnRoad`, `Delivering`…) — общий словарь, который DPD использует **и для движения к получателю, и для движения обратно в магазин** после `ReturnedFromDelivery`. Без разделения направления автосинхронизация могла бы отправить клиенту «заказ готов к получению» в момент, когда отправление едет обратно в магазин.

Решение нашлось в самой схеме, а не в тексте руководства: `stateParcel` в `tracing1-1?xsd=1` содержит поля `isReturn` (boolean), `dpdOrderReNr` и `dpdParcelReNr`, которых не было ни в `DpdStateItem`, ни в старом коде. `isReturn: true` однозначно помечает, что конкретная запись состояния относится к возврату — независимо от того, какой `newState` в ней записан.

Дополнительно исправлена ошибка выбора актуального состояния: код брал `states.at(-1)` (последний элемент массива), а документация DPD прямо говорит выбирать состояние **по `transitionTime`**, так как порядок массива не гарантирован. Теперь `getDataForRevise` сортирует `states` по `transitionTime` и берёт хронологически последнее.

Если у выбранного состояния `isReturn === true`, `unifiedCargoState` принудительно выставляется в `UnifiedOrderState.RETURNING` в обход `unifyParcelStatus` — иначе тот же `OnTerminalDelivery` на обратном пути снова дал бы `WAITING`. `RETURNING` (как и `PROBLEM`) уже обрабатывается в `reviseOrders()` как «не автопереход, сообщить сотруднику» — клиенту ничего не уходит, только алерт в Telegram. После этого исключение `cargo !== Cargos.DPD` снято: `WAITING`/`DELIVERED` для DPD теперь тоже проходят автосинхронизацию и уведомление клиента, как у Яндекс.Доставки/5Post/Почты.

Более богатый `event-tracking`/`getEvents` API (отдельные коды для доставки/возврата, явный параметр `OrderType (only for return)`) не потребовался — `isReturn` в уже используемом `tracing1-1` полностью закрывает вопрос направления, требует того же доступа и того же вызова, что уже был.

## Регистрация отправок из Telegram-бота (`/register`)

Менеджер без сессии сотрудника PrestaShop не может получить employee JWT с `yaSourcePlatformIds`/`fivePostSenderLocation` — эти настройки раньше попадали в NestJS только через JWT, подписанный модулем на странице заказа. Для бота это неприменимо: вебхук Telegram не связан ни с одним сотрудником.

Выбор между дублированием ID перевозчиков в переменных окружения сервера и новым техническим эндпоинтом модуля — в пользу эндпоинта: `id_reference` → тип перевозчика остаётся единственным источником правды в модуле (`carrierTypesByReference()`), как и для кнопок на странице заказа.

Модуль версии 1.8.0 добавляет `GET /module/shopserver/botorders`, защищённый общим ключом `X-ShopServer-Bot-Key` (по аналогии с `X-ShopServer-Cron-Key`). Эндпоинт отдаёт заказы со статусами 12 и 13 (те же статусы уже разделяют склад отправки Яндекс.Доставки на Ростов/Тулу — критерий «готов к регистрации» выбран не случайно) вместе с `reference`, фамилией получателя и типом перевозчика, а также сами настройки `yaSourcePlatformIds`/`fivePostSenderLocation`, чтобы серверу не нужен был второй запрос.

`BotController` показывает заказы с `carrier === 'yandex' | 'fivepost' | 'dpd'` — Почта России пока не регистрируется этим способом (см. «Незакрытые вопросы»), поддержку можно расширить по мере необходимости. Список заказов и настройки на выбор менеджера хранятся в `Map<chatId, …>` внутри контроллера — без TTL и персистентности между рестартами, как и `pendingYaReferences`.

`BotController` зарегистрирован в `AppModule`, а не в `BotModule`: команда `/register` вызывает `AppService.createYaOrder`/`createFivePostOrder`/`createDpdOrder` напрямую, а `AppModule` уже импортирует `ShopModule`, `YaModule` и `BotModule`. Регистрация контроллера в `BotModule` потребовала бы `forwardRef` в обе стороны (`AppModule` → `BotModule` уже существовал, а `BotModule` → `AppService` создал бы цикл) — вынесение контроллера в `AppModule` даёт тот же HTTP-путь `/bot/webhook` без циклических зависимостей модулей.

DPD не требует никаких дополнительных настроек сотрудника (в отличие от `yaSourcePlatformIds`/`fivePostSenderLocation`) — пункт выдачи для него уже приходит из переписки по заказу через `findPointId`, поэтому `AppService.createDpdOrder` в боте вызывается с одним `{ orderId }`, без второго аргумента.

Список выбора дополнен пунктом `0. Зарегистрировать всё`: команда обрабатывается как обычный номер (диапазон проверки расширен до 0), поэтому не потребовалось отдельного текстового распознавания. Заказы регистрируются последовательно, а не параллельно — параллельные вызовы одновременно бьют в лимиты Яндекс.Доставки, 5Post и DPD (SOAP), а `createYaOrder` и так делает внутреннюю паузу в 5 секунд перед проверкой созданной отправки. Итог приходит одним сообщением-сводкой (✅/❌ по каждому заказу) после завершения всех попыток, а не по одному сообщению на заказ, чтобы не упереться в лимиты Telegram при большом списке.

## Незакрытые вопросы

| Тема | Суть |
|---|---|
| Ключ виджета 5Post | Лежит в публичном JS витрины. Иначе виджет не работает; нужен ключ с привязкой к домену от 5Post. |
| Секрет вебхука Telegram | `POST /bot` не проверяет `X-Telegram-Bot-Api-Secret-Token` — можно слать поддельные апдейты. |
| Идемпотентность создания отправок | Повтор после таймаута может создать дубль в Яндекс.Доставке. Стало актуальнее после введения таймаутов. |
| Строгий TypeScript | `strictNullChecks` и `noImplicitAny` отключены — не ловятся падения при разборе ответов внешних API. |
| helmet и rate limiting | Отсутствуют. Логирование и обработка ошибок закрыты — см. раздел «Ошибки и диагностика». |
| Права сотрудников | Все с доступом к заказам имеют одинаковые возможности. |
| `pendingYaReferences` | Набор в `BotController` без TTL — запись живёт вечно, если после `/ya` не пришло следующего сообщения. |
| `pendingRegistrations` | То же самое для `/register` — без TTL, плюс любой сотрудник в чате менеджеров может зарегистрировать любой заказ из списка. |
| Почта России в `/register` | Не поддержана намеренно — регистрация отправок Почты России не реализована и на сервере (см. `PostService`). Заказы с этим перевозчиком не попадают в список бота. |
| Право PUT на `order_carriers` | Ключ webservice должен получить его вручную в БО модуля — код не проверяет и не предоставляет это право сам. |
| Повторная отправка письма о треке | Любая повторная запись трека (не только первая) шлёт письмо заново — исправление опечатки в треке тоже уведомит клиента. |
